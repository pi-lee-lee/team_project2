RViz 대신 웹 화면에서 로봇을 움직이는 구조

예전에는 RViz에서 2D Pose Estimate를 찍고 Nav2 Goal을 클릭했습니다. 지금은 그 두 동작을 웹 화면이 대신합니다. 웹 요청은 Django 서버를 거쳐 브리지 노드로 가고, 경로는 직접 짠 A*가 계산합니다. Nav2는 그 경로를 따라가는 역할(controller_server)만 맡습니다.

브라우저 Django 서버 (PC) ROS 2 노드 (PC) TurtleBot (Raspberry Pi)
비교

실행 순서: 예전과 지금

예전 방식 RViz

  1. Pi로봇 bringupros2 launch turtlebot3_bringup robot.launch.py
  2. PCNav2 + RViz를 한 번에 실행ros2 launch turtlebot3_navigation2 navigation2.launch.py map:=~/maps/xxx.yaml
  3. RViz2D Pose Estimate로 초기 위치 지정
  4. RVizNav2 Goal 클릭 → bt_navigator가 경로 계획부터 주행까지 전부 처리

지금 방식 웹 관제

  1. Pi로봇 bringup (예전과 같음)ros2 launch turtlebot3_bringup robot.launch.py
  2. 서버Django 실행 (HTTP + WebSocket, :8000)scripts/start_server.sh
  3. PCA* 플래너 + 브리지 노드scripts/start_bridge.sh maze_map
  4. PCNav2를 두 단계로 실행 (RViz 없음)scripts/start_nav2.sh ~/maps/maze_map.yaml
  5. 웹브라우저에서 http://<PC IP>:8000 → 초기 위치 지정
  6. 웹여기로 이동 또는 등록한 위치로 작업 시작 → 도착하면 적재 완료

전체 구성: 4개 영역과 그 사이 연결

웹과 ROS는 직접 연결되지 않습니다. 브라우저와 브리지 노드가 각각 Django 서버에 WebSocket으로 붙고, 서버가 둘 사이 메시지를 중계하면서 작업 상태를 DB에 기록합니다. rclpy를 Django 안에서 돌리지 않으려고 이렇게 분리했습니다.

시작 순서

켜는 순서와 각 단계에서 일어나는 일

Pi

robot.launch.py

/scan, /odom, TF odom→base_footprint, /battery_state가 나오기 시작합니다. 예전과 같습니다.

서버

start_server.sh

manage.py runserver 0.0.0.0:8000. 아직 로봇이 붙지 않아서 로봇 상태는 OFFLINE입니다.

PC

start_bridge.sh maze_map

astar_planner와 warehouse_bridge 두 노드가 뜹니다. 브리지가 서버에 접속하면 hello를 보내고, 서버는 로봇 상태를 IDLE로 바꿉니다. 이후 /map을 받으면 맵을 서버로 보내고, 서버는 maze_map 이름으로 PNG를 저장해 활성 맵으로 지정합니다.

PC

start_nav2.sh: 1단계 위치 추정

map_server와 AMCL만 먼저 띄웁니다. map_server가 /map을 발행하므로 A* 플래너와 브리지도 이때 맵을 받습니다. 스크립트는 TF map→odom이 나올 때까지 기다립니다.

웹

초기 위치 지정

지도에서 로봇 위치를 클릭하고 방향을 드래그합니다. 서버를 거쳐 브리지가 /initialpose를 발행하면 AMCL이 map→odom TF를 내기 시작합니다. 위치를 자동으로 맞추려면 tools/localize.py를 써도 됩니다(LiDAR 스캔을 맵에 대조해서 초기 위치를 보냄).

PC

start_nav2.sh: 2단계 주행

map TF가 확인되면 navigation_launch.py(controller_server 등)를 띄웁니다. 이제 이동 명령을 받을 수 있습니다.

왜 Nav2를 두 단계로 나눴나 한 번에 띄우면 controller_server가 AMCL의 map→odom TF를 끝까지 받지 못하는 경우가 있었습니다. 그러면 TF 오류 직후 "Reached the goal!"을 돌려주고 로봇은 움직이지 않습니다. 그래서 브리지는 Nav2가 성공이라고 해도 실제 위치와 목표 사이 거리가 0.3 m를 넘으면 실패로 처리합니다.
이동 한 번의 흐름

"여기로 이동"을 클릭하면

작업 흐름

여러 위치를 돌고 홈으로 돌아오는 작업

위치 목록에서 여러 곳을 고르고 선택한 위치로 작업 시작을 누르면, 서버가 고른 순서대로 단계를 만들고 마지막에 홈 복귀 단계를 붙입니다. 물류 위치에 도착하면 로봇은 멈춰서 기다리고, 사람이 적재 완료를 눌러야 다음 위치로 갑니다.

    WAITING_LOAD --> MOVING: 적재 완료 (다음 단계)
    MOVING --> MOVING: 홈·지정 지점 도착 후 다음 단계
    MOVING --> IDLE: 마지막 단계 도착 (작업 완료)
    MOVING --> ERROR: 이동 실패
    ERROR --> MOVING: 재시도 / 건너뛰기
    ERROR --> IDLE: 작업 취소 · 오류 해제
    MOVING --> ERROR: 비상정지
    IDLE --> OFFLINE: 연결 끊김
    MOVING --> OFFLINE: 연결 끊김

브리지가 다시 접속하면 hello에 진행 중이던 goal_id를 실어 보냅니다. 서버 기록과 같으면 MOVING을 이어가고, 다르면 ERROR로 두고 재시도를 기다립니다.

메시지 규격

WebSocket으로 오가는 JSON

웹→ 서버 (action)

  • goto_point지도 위 임의 지점
  • start_task위치 여러 개 + 홈 복귀
  • goto_location위치 하나 (복귀 없음)
  • confirm_load적재 완료
  • retry_step실패한 단계 다시
  • skip_step현재 단계 건너뛰기
  • cancel_task작업 취소
  • go_home홈 복귀
  • estop비상정지
  • set_initial_pose초기 위치
  • save_location위치 추가·수정

서버→ 브리지 (type)

  • gotogoal_id, x, y, yaw
  • cancel현재 목표 취소
  • stop취소 + cmd_vel 0을 1초
  • initial_pose/initialpose 발행

브리지→ 서버 (type)

  • hello접속 시, 진행 중 goal_id
  • mapOccupancyGrid (zlib+base64)
  • pose5Hz, DB 저장 안 함
  • pathA* 경로 (3점마다 1개)
  • battery5초마다
  • nav_statussucceeded / failed / canceled
